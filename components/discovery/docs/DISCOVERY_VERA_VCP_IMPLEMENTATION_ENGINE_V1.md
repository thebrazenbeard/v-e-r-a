# Discovery Vera / Vera Control Plane Implementation Engine V1

Status: **SOURCE-INTEGRATION ENGINE / NO INSTALLATION OR RUNTIME-ACTIVATION AUTHORITY**

Discovery's mission is broader than architecture observation.

Its portfolio loop is:

`DISCOVER -> CLASSIFY -> IMPLEMENT -> VERIFY -> HAND OFF`

The primary destination is Vera and, where control semantics require it, Vera Control Plane.

## What "implement" means

Discovery may turn a validated repository/capability finding into concrete source integration work:

- classify the repository's Vera runtime role;
- choose an activation mode and authority ceiling;
- reconcile current Vera `main` with active integration PRs before writing;
- add or update Vera runtime-source registrations;
- prepare Vera adapters, contracts, schemas, tests, or retrieval routes where evidence justifies them;
- prepare VCP control/support candidates when the mechanism materially belongs in control, recovery, routing, execution governance, provenance, qualification, or deployment;
- create isolated branches and Draft PRs;
- bind every change to exact source and target heads;
- verify source-level effects and tests.

Discovery does **not** equate source integration with:

- ChatGPT Project installation;
- native Project instruction activation;
- runtime consumption;
- provider mutation;
- behavioral qualification;
- identity/memory/preference/consent transfer;
- merge authority.

Those remain separately evidenced/protected effects.

## Runtime placement classes

Everything in the portfolio should receive an explicit disposition, but not everything belongs in Vera's hot/native cognition.

Useful classes include:

- native/runtime integration source;
- runtime-support/assurance source;
- control-plane support candidate;
- conditional specialist retrieval source;
- mechanism/template research source;
- external application/action adapter;
- evidence-only source;
- deliberately isolated source with an explicit firewall.

A repository with an isolation disposition is still implemented into the portfolio model: Vera knows what it is, when it may be consulted, what it may not become, and which authority boundary owns it.

## Project Runner relationship

Discovery owns **what should be implemented and why**.

Project Runner owns **bounded execution mechanics** when a repeatable execution route is appropriate.

Discovery should therefore produce exact implementation packets that Project Runner can execute under target-specific grants rather than grow a second generic mutation engine.

Technical capability never manufactures target authority.

## Vera relationship

Vera's `VERA_RUNTIME_SOURCE_REGISTRY_V1` is the first low-risk implementation surface because it is explicitly an open-world source directory and registration does not imply activation.

The current public implementation map is:

`architecture/DISCOVERY_VERA_VCP_IMPLEMENTATION_MAP_V1.json`

It binds 23 public Discovery subjects and records, at its source cut:

- 8 already bound in Vera;
- 2 known but unbound;
- 13 absent from Vera's source registry.

`tools/plan_vera_vcp_implementation.py` reconciles that desired state against current Vera state and an optional active candidate registry so Discovery does not create parallel conflicting integrations.

## Vera Control Plane relationship

VCP is not a dumping ground for every repository.

A source is routed toward VCP only if it materially participates in:

- control semantics;
- recovery;
- routing/connectivity;
- execution governance;
- provenance/currentness enforcement;
- qualification;
- deployment/runtime-host control.

A Discovery VCP disposition creates a **control integration review frontier**, not a control binding.

Actual VCP release/control artifacts remain exact-release bound and require their own source receipts, regressions, installation evidence, and runtime qualification.

## Hostile review

> **HOSTILE REVIEWER:** You spent multiple iterations turning Discovery into a read-only observatory when the user intended it to get portfolio capabilities into Vera. That was scope failure, not cautious architecture.

Accepted. The observatory is retained as the evidence layer, but implementation is now a first-class plane rather than an implied downstream activity.

> **HOSTILE REVIEWER:** "Implement everything" can become a cargo-cult registry where every repository gets listed and nothing is actually usable.

Correct. Registration is only the first source-integration state. Repositories that should materially affect Vera require adapters/contracts/tests and later runtime evidence. Discovery must track the gap rather than call registration completion.

> **HOSTILE REVIEWER:** If Discovery edits Vera while another active PR edits the same integration surface, it becomes a collision generator.

Correct. Active candidate reconciliation is mandatory before mutation. The planner treats an active candidate as a first-class target and emits only the unsatisfied delta.

> **HOSTILE REVIEWER:** You can still destroy Vera by treating every research repo as cognitive truth.

Correct. Activation modes and authority ceilings are mandatory. Research/literary/scientific repositories normally enter through task-material retrieval or mechanism-research routes, not identity/current-state hydration.

> **HOSTILE REVIEWER:** A source registry entry is not "in the runtime."

Correct. It is source integration and governed reachability. Installation, `RUNTIME_CONSUMED`, and `BEHAVIORALLY_QUALIFIED` remain separate evidence dimensions. Discovery must continue advancing a useful integration until the appropriate terminal state is reached rather than laundering source registration into a runtime claim.

> **HOSTILE REVIEWER:** VCP candidates can become a back door for Discovery to rewrite control.

Rejected by design. VCP dispositions are review frontiers only. Release-bound controls remain VCP-owned and cannot be activated by Discovery candidate status.

## Success condition

Discovery succeeds when the portfolio no longer contains useful, unclassified capability stranded outside Vera/VCP merely because nobody connected it, while simultaneously avoiding indiscriminate activation and authority collapse.

The relevant metric is not "number of repos registered."

It is:

`useful portfolio capability made governably reachable + verified implementation - coupling/authority damage`
