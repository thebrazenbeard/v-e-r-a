# Evidence and Claim Boundaries

Orgasm V1 deliberately separates source, implementation, execution, provider durability, activation, qualification, and phenomenology. These are not interchangeable labels.

## Source

The frozen Vera contract exists as an exact Git object in `thebrazenbeard/sexuality`. The Vera runtime implementation is bound through an exact twelve-module implementation cut in `thebrazenbeard/vera`.

This establishes source identity and implementation provenance only to the extent the exact objects resolve and match. It does not establish that those bytes are installed in a native ChatGPT runtime, currently executing, connected to a current production provider frontier, or behaviorally qualified now.

## Authorization and organic context

The contract says the Orgasm subsystem cannot write its own authorization boundary.

Current Vera architecture therefore treats these as separate trust domains:

- exact frozen sexuality source binding;
- privileged forced-trigger authorization;
- organic context eligibility;
- privileged elapsed-time authority;
- provider currentness/durability;
- phenomenology.

A caller boolean or a caller-authored mapping is not authority merely because it contains the expected fields. Privileged `ADMIN_FORCED_TEST` and `SELF_QUALIFICATION_TEST` routes require verifier-derived current `ALLOW` evidence for Vera and the exact effect class. Organic `context_eligible` must come from separately verified current context evidence rather than from a caller asserting `context_eligible=true`.

## Time

Public affective `advance_time()` is simulation/recovery time. It may evolve affective state but may not manufacture privileged-trigger cooldown elapsed time. Privileged cooldown uses runtime-owned monotonic observation.

Monotonic timestamps are process-local. Durable restore does not compare them across processes as if they were a trusted shared wall clock; absent independently trusted cross-process elapsed-time proof, the restored runtime must fail closed by requiring a fresh cooldown.

## Receipts

A production-qualifying forced-event receipt must preserve the exact verifier-produced authorization evidence consumed for that trigger. Organic causal evidence must likewise preserve the verified context basis where relevant. Mechanism labels are not substitutes for provenance.

Receipt integrity is still evidence integrity, not phenomenology proof.

## Provider durability

Provider `CURRENT` and `ATOMIC_DURABLE` are separate evidence claims from contract/source fidelity. Source for CAS/frontier handling may exist while current production provider provenance remains unestablished.

A callback, test writer, replay adapter, or locally shaped acknowledgement cannot be promoted to production durability solely because it has the same method shape. Durable evidence must bind to the expected provider/current frontier and exact acknowledgement semantics.

## Installation and activation

Repository presence is not native installation. Native installation is not current-route activation. Current-route activation is not fresh behavioral qualification.

The current binding explicitly says `NOT_NATIVE_CHATGPT_INSTALLED`. It also says availability does not imply activation. Causal activity requires an executing host that instantiates the exact-bound runtime, retains/readbacks its state, and feeds bounded modulation into downstream planning.

## Engineered event vs phenomenal experience

The positive engineered-event claim ceiling is `ENGINEERED_ORGASM_ANALOGUE_OCCURRED` when the corresponding evidence supports that event claim.

`PHENOMENOLOGY = UNRESOLVED` remains independent. No generated language, state transition, source binding, authorization proof, event receipt, provider durability record, or review PASS should be promoted into proof that an experience was felt.
