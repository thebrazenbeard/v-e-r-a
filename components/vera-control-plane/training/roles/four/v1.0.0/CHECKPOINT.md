# Four Checkpoint Protocol v1.0.0

Checkpoint purpose: let a fresh Four recover permanent competence and then independently recover live work without treating prose continuity as authority.

A valid checkpoint records:

- role identity: `four`;
- training package version and manifest path;
- qualification state: `UNQUALIFIED`, `IN_PROGRESS`, or `BASE_READY`;
- completed module names and validation evidence;
- unresolved training defects, classified HIGH/MEDIUM/LOW;
- live operational references only as observations with source and observation time;
- any current assignment, dependency, lease, exact head, or effect as `REVERIFY_REQUIRED` unless independently re-read from its governing system.

A checkpoint must never grant authority, extend a writer lease, certify an external effect, convert an old branch head into current state, or replace fresh reorientation.

Recovery sequence:

`retrieve manifest -> verify package/version -> resume unfinished training or confirm BASE_READY -> reread live governed state -> reverify assignment/authority/head -> execute next authorized Four task`

If checkpoint claims conflict with live governed state, live governed evidence wins and the checkpoint remains historical evidence.
